## This iteration

The previous build embedded its UTC build date into every sitemap entry as `lastmod`. A rebuild does not necessarily change a page's significant content, and D1-backed content may change separately. The same source also generated different Worker bytes when built on different dates. Google recommends that `lastmod` accurately reflect a significant page update and states that it ignores `changefreq`: https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap

The candidate omits these unsupported fields, retaining all 39 canonical URLs and preview noindex behavior. It removes the wall-clock date from the build. A regression test builds in an isolated temporary directory with clocks on either side of midnight and compares artifact hashes; the test failed on the original source and passed on the modified source. Equal builds from equal inputs do **not** prove that any particular Cloudflare deployment uses those bytes; retain and compare the tested artifact at release time.

Local evidence: built Worker 369,888 bytes; 116 offline Node tests passed, including the new cross-date test; source CSS 74,888 bytes; client JS 9,062 bytes. The separate live recovery test could not reach its external target from this environment and is not counted as passed. No browser, current Lighthouse, screen-reader or Cloudflare candidate deployment test is represented by these local numbers.

## Prioritized next actions

1. **Release integrity:** provide authorized Cloudflare release access to the existing Direct Upload project and preserve the 25-file manifest and bindings. Build once, retain the artifact and its SHA-256, deploy a unique read-only/noindex preview, test that exact candidate, compare the uploaded Worker bytes, and only then consider production promotion and verification. Avoid overlapping releases.
2. **Candidate QA:** run the sitemap routes, trilingual mobile/desktop interactions, no-write admissions flows, automated accessibility plus manual keyboard/screen-reader checks on the exact preview. Add 320, 390, 768, 1024, 1440 and 1920 px screenshot/overflow coverage. The current local environment did not validate these.
3. **Baseline measurement:** measure the actual canonical production host and exact candidate with current Lighthouse and field LCP/INP/CLS where available, without confusing lab results with real-user percentiles. Check and update the outdated baseline target and record reproducible context.
4. **Institutional accuracy:** confirm current intake, counts, program details, fees, schedule, image rights and appropriate trademark permissions with authorized staff. Do not infer validation from their presence in the existing CMS or prior copy.
5. **Content and design:** independently review the three languages, accessibility and course journeys; compare with education benchmarks and avoid duplicating in-flight work in #56 and #58. British Council's skill/level organization and ETS's accessible preparation resources provide useful patterns, not permission to copy content: https://learnenglish.britishcouncil.org/free-resources/reading and https://www.ets.org/toefl/test-takers/ibt/prepare.html
6. **Security and recovery:** separately qualify authenticated staff workflows and an independent encrypted backup/isolated restore. No production database changes, real applications or test messages were performed in this iteration.
