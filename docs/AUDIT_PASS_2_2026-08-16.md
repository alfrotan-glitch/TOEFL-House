# Independent adversarial audit — pass 2

Continuation of the production-readiness effort. Pass 1 (`REMEDIATION_2026-08-16.md`)
closed the financial findings F-1…F-4. This pass audited the areas pass 1 did
**not** reach: authorization depth, dead code, and whether the quality gates
themselves are real.

Everything below was reproduced with executable evidence against the running
API before any code was changed.

---

## F-5 — a scoped owner grant conferred global superuser (HIGH, fixed)

**Reproduction.** Granted the `owner` role scoped to a single campus, then
logged in as that user:

```
foreign-campus student rows returned : 1   ("OtherCampus Secret")
GET /finance/overview (foreign)      : 200 with another campus's finance
GET /users                           : 200, all 10 users
POST /branches                       : 201
```

**Root cause.** Every superuser short-circuit in the codebase called
`hasRole(ctx, 'owner')`, which ignores scope entirely — `canAccessBranch`,
`canAccessAllBranches`, `authorize`, `requirePermission`, plus the
bos/branches/events/auth route guards. `user_roles.scope_type` and `scope_id`
were written on the grant and then never consulted for owners, so scoping an
owner grant did *nothing at all*.

**Fix.** `isGlobalOwner(ctx)` — true only for an **organization**-scoped owner —
replaces the bare role check at all nine bypass sites. Safe because both the
seeded owner and the `LEGACY_ROLE_MAP` fallback are organization-scoped, so
every legitimate owner keeps every power (verified live, before and after).

**After:**

```
foreign-campus rows across /students /payments/balances
  /teachers /classes /visitors                : 0
GET  /students/<foreign id>                   : 403
POST /students/<foreign id>/payments          : 403
real org-scoped owner: /users 11 · /students?branchId=all 6 · roles 10
```

**Accepted by design, documented:** a campus-scoped owner still passes
*endpoint* gates (`/users` 200, `POST /branches` 201) because the owner role
carries all 99 permission codes. Scope governs **which rows**, not **which
endpoints**. Only the data-isolation half was exploitable and it is closed.
Narrowing the endpoint half would change the product's permission model, which
is a product decision rather than a defect.

## F-6 — any teacher could rewrite any colleague's grades (HIGH, fixed)

**Reproduction.** Two teachers in the same branch. A user linked to teacher A:

```
PUT /api/classes/<class taught by teacher B>/grades   { score: 99 }
-> 200 {"ok":true,"count":1}
```

The row persisted in `student_grades` with `graded_by` = teacher A's user id.
Teacher A could also read the colleague's full gradebook, its per-student edit
history, and the class lifecycle.

**Root cause.** `requireClass()` authorized on **branch** only, and colleagues
share a branch. `canAccessClass`/`assertClassAccess` had been written in
`core/rbac/abac.ts` for exactly this rule and **were never called from any
route** — the module was reachable only from a unit test.

Two things made this durable:

1. That unit test passed for the entire vulnerable period. It proved a
   *function*, not a *route*, and created the appearance of enforcement.
2. `sessions.routes.ts` **did** enforce ownership (`assertCanMarkSession`), so
   the two halves of one teaching workflow disagreed — a teacher could not mark
   a colleague's attendance but could rewrite their grades.

**Fix.** `requireClass()` now applies `assertClassAccess()` whenever the caller
is class-scoped, so every current and future `/classes/:id` endpoint inherits
the rule centrally instead of each route remembering it. Managers and owners
are branch-scoped and unaffected.

**A test had encoded the vulnerability.** `grade-lock-workflow.test.ts` seeded a
teacher user linked to *no* teacher profile, grading a class with *no* teacher
assigned, and asserted success. Repaired to model a real owning teacher, then
mutation-checked (forcing `canEditGrades` to `true` still fails it) to confirm
the grade-lock coverage it exists for was not weakened to accommodate the fix.

## The quality gate itself was partly fictional

`server`'s `lint` script was `tsc --noEmit`, and the root `lint` only covers the
frontend `src`. **Nothing in the repo ever ran eslint over `server/src`** — so
every previous "lint clean" claim was a statement about type checking only.
Switching it on surfaced 7 real errors that had accumulated unnoticed.

`server.lint` is now `eslint src scripts && tsc --noEmit`, and all 7 are fixed
(2 redundant initializers — verified harmless, not logic bugs; 1 `prefer-const`;
3 `require()` imports in tests; 1 orphaned prepared statement).

## Dead code removed

Nine exported functions had no caller anywhere in backend, frontend, scripts or
tests. Worth singling out: **`setMainBalance` overwrote a finance account
balance outright, bypassing the ledger.** An unused absolute-write helper
sitting beside the incremental ones is an invitation to reintroduce a second
source of financial truth, so its removal is an integrity win, not tidying.

Two candidates were investigated and **kept**: the unused `jalali` exports (the
server file is a mirrored copy of the frontend module, enforced by a test) and
the two placement route files that appear unmounted in `index.ts` but are
composed into `placement.routes.ts`.

## Remaining risks

- **Endpoint-level owner permissions** are scope-independent (see F-5). Data is
  isolated; endpoint gates are not. Deliberate, documented, product decision.
- **Employee pay-salary** duplicate guard is free-text `LIKE` matching, so it is
  bypassable via `paymentType:'advance'` or a varied `monthName`, and it lacks
  the F-4 idempotency key. Low severity, still open.
- **CI is inactive** — `ci/github-actions-ci.yml` is not wired up, so none of
  these gates run automatically. Now that server lint is real, this is the
  highest-value remaining infrastructure gap.
- Single-process SQLite ceiling; no horizontal scaling story.
- 576 `any` in server source; no frontend test runner; backups local-only.
- Dev DB is polluted with probe fixtures from both audit passes.

## Verdict

The two authorization findings in this pass were **both real, both HIGH, and
both invisible to the existing test suite** — one because a test proved a
function nobody called, the other because a test had encoded the vulnerable
behaviour as expected. Combined with a lint gate that never ran, the recurring
theme is that **the green signals were weaker than they appeared.**

The fixes are architectural (one central choke point each) rather than
per-route patches, and each is mutation-verified. Financial integrity, DB
integrity and campus isolation all verify clean.

**Not yet production-ready** — not because of a known open hole in the paths
audited, but because CI does not run and the audit surface is not exhausted.
The blocker to a "ready" verdict is automation, not a specific unfixed defect.
