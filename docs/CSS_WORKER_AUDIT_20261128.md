### CSS cascade and tokens

- A PostCSS inventory of the baseline found 1,011 rules, 2,981 declarations and 887 distinct `(media context, selector)` pairs, with 12 `!important` declarations. Multiple overrides were concentrated in typography, homepage cards, headers, and mobile admissions; for example `.course-card` appeared four times in the base context. A repeated selector is not in itself safe to delete: shorthand interactions, state, specificity, condition and fallback matter.
- The candidate retains 994 rules, 2,854 declarations and nine `!important` declarations. The refactor removed 134 earlier declarations only where the exact same selector and enclosing condition had a later declaration of the same property and importance, and either the value was identical or the later value was a conventional numeric/hex literal. Modern-value fallbacks, different selectors, different media contexts and shorthands were not broadly purged. A few link-hit-area declarations were then consolidated in their original rule. The exact candidate requires the regression checks below, not the source inventory alone.
- Existing red/white/ink/paper design values are now centralized in one `:root` block, with 179 literal color uses changed to existing tokens; white/surface and focus aliases share those tokens. No institutional color or logo was replaced. The reusable `.shell`, `.button`, `.growth-card` and logical-direction properties remain shared. English is LTR; Dari and Pashto retain language-specific typography and `[dir=rtl]` rules rather than a duplicate stylesheet.
- Selector parsing found 1,109 selector-list entries, eight containing an ID and 29 rules explicitly using `[dir=rtl]` in the candidate. This is an inventory, not a complete computed-specificity analysis: functional pseudo-classes and nesting make a simple count insufficient. High-specificity overrides remain, especially mobile EAP/admissions; review them against real states before removal.
- Breakpoint inventory: 1200 (2 media blocks), 1020 (5), 970 (1), 960 (1), 760 (17), 460 (7), 390 (3), 360 (1), plus reduced-motion and forced-colors conditions. Repeated blocks cannot be mechanically combined without moving rules across the cascade. Consolidate them incrementally by component only after testing their ordering and edge widths; there is no claim that breakpoint cleanup is finished.
- Literal class search identified `.original-form`, `.growth-main` and `.growth-wrap` as absent from the current `site-v2` JS/MJS sources. This is not proof that CMS/legacy markup, content or dynamically constructed classes cannot use them. They were **not** removed. Class searches, CSS coverage, one browser and screenshots cannot establish complete dead-code safety.
- Chromium CSS coverage on all 51 routes at 390 and 1440 pixels with synthetic CMS measured 7,057–32,194 of 74,497 shipped bytes used per initial page (mean 12,166); union across the 102 initial states was 66,085 bytes. This suggests page-specific CSS might reduce first-route transfer, but approximately 14.8 KB gzip is cached across the site and splitting would introduce more requests, asset/version management, cache and conditional-loading failure modes. Hidden menus, hover, focus, expanded details, runtime content and other viewports were not covered. Keep a shared file until a real Pages preview compares cold/warm navigations, bytes, LCP, CLS and failure states; do not delete the unobserved remainder or add infrastructure on this evidence.

## Worker structure and boundaries

`build.mjs` assembles the existing edge Worker with authored renderers and static locale content, then embeds the shared CSS and JS. The output is a generated single Worker; source lines and deployed uncompressed bytes are different questions. Source module byte inventory: edge 16,764; landing 83,483 (including an 18,420-byte base64 logo, 13,814 decoded bytes); detail 24,065; General English 37,653; EAP 43,292; special programs 54,125; guides approximately 45.5 KB; public content 3,288; CSS 74,697; JS 9,623. The builder also compacts selected static locale objects; these source sizes must not be added as if they were transfer bytes.

- Route lists in the edge layer feed the sitemap and guide renderer. `v2Home`, `v2Detail`, `v2Guides` and program renderers share headers, footers, SEO, content escaping and the asset revision. Repeated editorial strings and HTML are substantial; improve component boundaries with tests rather than extracting every template into an abstraction.
- `CMS_DB` provides public localized content with reviewed fallback behavior; `LEGACY_CMS` remains a separate service boundary for protected retained CMS routes; `ASSETS` supplies the retained manifest. The preview blocks non-read methods; admin and retired tools have separate security logic. Do not collapse those boundaries, replace bindings, proxy the retired origin, or write production data.
- The build currently performs string insertion into the edge entrypoint and uses shared lexical scope. Sentinel checks and reproducibility tests reduce risk but do not provide module isolation or type checking. A future change should replace this brittle composition only after route, asset, binding, security and exact-candidate parity tests are available. Splitting into Workers or moving embedded assets changes failure and deployment behavior without proven latency/size benefit; neither was done.
- A shared `v2FontPreload` now supplies the existing checksum-pinned RTL font early to Dari/Pashto subpages as well as homepages; English does not preload it. No new font, host or third-party service was added. This fixes duplicated preload markup without altering the CSS asset or CMS binding.

## Visual and functional evidence

The screenshot harness can capture 306 top-of-page screenshots (`TOEFL_VISUAL_DIR`) and 102 full-page screenshots at 390/1440 (`TOEFL_FULLPAGE_DIR`) from 51 sitemap routes. CI uploads both sets as temporary artifacts and runs full-page axe at 390 in all 51 routes. `visual-compare.mjs` compares same-environment PNG bytes and flags missing, added and unallowed changes; it is deliberately strict and does not silently discard pixel changes.

- Baseline versus cascade-only pass: 306/306 viewport PNGs and 15/15 representative component PNGs were byte-identical. After intended visual changes and token/preload work, 279/306 viewport PNGs were byte-identical. The English homepage changed at 1024/1440/1920 and the three localized guide indexes at all six widths, as intended. Six Pashto admissions viewport PNGs differed by 20 pixels each in native control rendering; this was investigated, not counted as proof of a design change. In the 102 full-page comparison, 92 were byte-identical; six guide indexes and English desktop homepage were intentional changes; English mobile and two Pashto home screenshots differed by four anti-aliased video-frame pixels each. These pixel results are synthetic and do not eliminate the need for manual visual review.
- English desktop homepage heading was resized so the assessment and program actions appear within the 1440 × 900 viewport rather than below it. Library cards now use restrained editorial numbering and the existing brand red. Numbering is hidden from assistive technology, names remain available, and RTL text isolates English titles. These are limited improvements, not a complete flagship redesign.
- 120 offline Node tests passed. Browser checks cover 51 routes × six widths, no horizontal overflow and one H1; full-document axe WCAG 2/2.1 A/AA tags on 51 initial mobile states reported zero violations. Twelve book main regions and three interactive practice panels were also checked. Keyboard menu/focus restoration, whole-card native hit target at 390/1440 in three languages, practice feedback/reset, preview POST denial, and no-JS menu/practice fallback were exercised. This does not establish WCAG 2.2 conformance, full keyboard/screen-reader support, authenticated CMS workflows, real image loading, or all interactive states.
- Screenshots use the vendored font, synthetic CMS, blocked external networks and absent production images. Broken image placeholders are a fixture limitation, not a proposed replacement for institutional photography. Files are local under `.sandbox/visual-before`, `.sandbox/visual-release-candidate`, `.sandbox/fullpage-before`, and `.sandbox/fullpage-release-candidate`; CI artifacts expire. No claim is made that every full-page screenshot has been manually reviewed.

## Synthetic performance sample, not deployment evidence

Lighthouse 12.8.2 mobile, Chromium 138, local HTTP adapter, synthetic CMS and font, blocked external network/assets and preview `noindex`; single samples, not field measurements. The reproducible local-only adapter is `cloudflare/site-v2/synthetic-lighthouse.mjs`; it uses temporarily installed Lighthouse, never real bindings. Nine localized home, guides and admissions pages measured performance 98–100 except Pashto admissions 99, accessibility 100, best practices 96 on home and 100 on guides/admissions, SEO 69 because `is-crawlable` correctly fails for the noindexed preview. LCP ranged about 1.51–2.34 seconds and CLS was 0 in these post-preload samples. Prior individual samples of Pashto admissions and Dari guides were 0.0967 and 0.0666 CLS respectively before subpage font preload; after preload both measured 0 in the local samples. Network, font-cache, authentic images and runtime differences require repeated measurement on an authorized exact preview. Total blocking time is not field INP. No live Lighthouse, genuine image, binding, SEO crawlability or production Web Vitals claim follows from this experiment.
