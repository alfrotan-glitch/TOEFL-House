## F-7 — authorization used the caller's *home branch*, not their scope (fixed)

Thirteen sites compared a resource's branch against `user.branchId` — the
single branch stored on the user row — instead of asking whether the caller is
authorized for that branch.

```
owner (home branch "1"), acting on another branch:
  POST /api/impact/stories        -> 400  "must belong to the same branch"
  POST /api/class-teacher-skills  -> 403  "Teacher belongs to another branch"
```

In the skills case the owner had just created **both** the teacher and the
class in that branch through the API and was then refused permission to link
them. `class_teacher_skills` drives teacher payroll, so a real money-affecting
workflow was blocked for every multi-branch user. In `impact.routes.ts` the
contradiction sat on adjacent lines: `canAccessBranchResource()` authorized the
request and the next statement rejected it.

Two defects shared one root cause:

1. **Authorization.** Home-branch equality is not an authorization check. It is
   simultaneously too strict and disconnected from the RBAC scope model used
   everywhere else. Now uses `canAccessBranchResource` / `resolveBranchScope`.
2. **Data attribution.** Created rows stored `user.branchId` as their own
   branch, so a story about a branch-B student, or a skill assignment for a
   branch-B class, was filed under branch A. Payroll and impact reporting
   aggregate by branch, so per-branch figures were silently misstated. The
   branch now derives from the subject.

Because this fix **grants** access, the negative was proven too: a
branch-limited manager still gets 403 and writes no row, and a campus-scoped
owner shows 0 cross-branch leaks.

`students.routes.ts:402` was reviewed and deliberately **left** as home-branch
equality — it pins a student-portal account to its own branch, which is correct.

## F-8 — the ledger's "Period income" was a sum of the visible page (fixed)

The finance Ledger panel rendered *Period income / Period expenses / Net* as
`rows.reduce(...)` over the **current page**. With 90 transactions and a 50-row
page it reported **0 AFN income against a true 700 AFN**.

This is the dangerous class of financial bug: understated, plausible, no error
raised, drifting further from reality with every transaction recorded.

Two things kept it alive:

- The file's own header comment asserted *"the backend is the single source of
  financial truth"* while the code below did the opposite.
- The **identical defect had already been found and fixed** on the dashboard
  KPI tiles, whose comment documents a 99,311 AFN shortfall from the same
  cause. The pattern was known; this instance was missed.

Fixed by taking totals from `/finance/pnl` (SQL aggregate over the whole
period) and rows from `/finance/transactions?includeTotal=1` — an endpoint
capability that already existed and was unused. While totals load, the panel
shows "Period totals loading…" rather than a page-derived guess.

Sibling aggregates were audited rather than assumed: books/funding sum
client-side but their endpoints return unbounded lists, so those totals are
complete today (noted as a scale risk); the dashboard 7-day sparkline stays
page-derived and is now documented as SHAPE-only.

## Branding

The brand was retyped as a literal in ~20 components, which had produced
**seven** spellings of one institute name — *The TOEFL House*, *The TOEFL House
Academy*, *The TOEFL House Higher Education*, *TOEFL House ERP*, *The TOEFL
House ERP*, *TOEFL House*, *TH*.

Worse, **five surfaces drew a hand-made substitute for the logo**: the printed
student ID card and exam certificate rendered a coloured disc containing "TH",
the sidebar used a generic graduation-cap icon, and the login screen and
student portal each had their own "TH" block. Customer-facing printed documents
were going out with an invented mark.

`index.html` also referenced `/favicon.svg`, **a file that does not exist
anywhere in the repository** — the app had been shipping a broken favicon.

Now centralised in `src/config/branding.ts` (`BRAND_NAME`, `BRAND_SLOGAN`,
`BRAND_LOGO_URL`, `BRAND_NAME_DARI`, `brandLogoAbsoluteUrl`,
`brandPrintHeaderHtml`) plus `BrandLogo.tsx`. The official slogan **"Unlock the
world with TOEFL"** now appears on login, sidebar, ID cards, receipts and print
headers. Every branded surface was converted.

Two judgement calls:
- `BRAND_NAME_DARI` preserves the pre-existing Dari ID-card localisation rather
  than overwriting it with English — an existing functional requirement, not an
  invented alternative brand.
- `brandLogoAbsoluteUrl()` exists because print popups resolve relative URLs
  against `about:blank`, which would have rendered a broken image on every
  printed receipt and ID card.

### ⚠ Branding blocker

`public/brand/toefl-house-logo.png` **is absent.** The official PNG did not
reach the workspace (`/home/user/uploads/` never existed). Every consumer is
wired to that one path; dropping the file in completes the work and turns the
suite green.

**No recreated, redrawn or approximated logo has been committed**, per the
explicit instruction. `branding-consistency.test.ts` fails on this deliberately
rather than hiding it — it is the one intentional failing test in the suite.

## Remaining risks

- **CI inactive** (above) — the single largest gap.
- **Official logo missing** — branding is wired but the asset is absent.
- Owner role carries all 99 permission codes regardless of scope; scope governs
  rows, not endpoints. Deliberate, documented (pass 2).
- Employee pay-salary duplicate guard is free-text `LIKE` matching, bypassable
  via `paymentType:'advance'` or a varied `monthName`; lacks the shared
  idempotency key. Low severity, still open.
- `bos`, `exams`, `finance`, `placement-attempt`, `visitors` write money without
  `resolveIdempotency`. Probed under concurrency and found correct today
  (business-event guards + DB constraints), but they rely on SQLite's
  synchronous driver rather than a shared mechanism.
- Books/funding list endpoints unbounded — correct now, a scale risk later.
- Single-process SQLite ceiling; no horizontal scaling story.
- Three oversized modules; 576 `any` in server source; no frontend test runner;
  backups local-only.
- Dev DB polluted with probe fixtures from three audit passes.

## Verdict

**Not production-ready — two blockers, both external to the code.**

1. **CI is inert.** Nothing verifies this system automatically. Proven, not assumed.
2. **The official logo is missing**, so branded output is incomplete.

Neither is an unfixed defect in the application. Every defect found across three
passes is fixed, mutation-verified, and covered by a regression test.

The honest summary of three passes: **each pass found real HIGH-severity issues
the previous one missed, and in every case the existing tests were green
throughout.** Pass 2 found a scoped owner acting globally and a teacher
rewriting colleagues' grades; pass 3 found authorization keyed to the wrong
branch field and a financial total computed from a page. The recurring lesson is
that green signals were consistently weaker than they appeared — a lint script
that only ran the type checker, a test proving a function no route called, a
fixture encoding the vulnerability as expected behaviour, and my own first F-8
test that a mutant walked straight through.

Treat the unaudited surface as unproven rather than safe.
