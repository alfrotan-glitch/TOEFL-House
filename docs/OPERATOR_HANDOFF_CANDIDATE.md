# Cloudflare candidate handoff — safety gates

This document is for the separate authorized release operator. An artifact is **not an approval to deploy**. The release is held until the complete checklist is satisfied and the owner has explicitly approved publication of the adapted mini-practice from PR #56. PR #58's library is also adapted into #61; avoid a duplicate merge. PR #60 is separate and requires the owner-provided images and its own review.

## Identify exactly what is being evaluated

1. Obtain the source commit and tested build ref from `PACKAGE-INVENTORY.json` in the **`toefl-unapproved-candidate-with-historical-assets`** artifact of the applicable [quality-gate run](https://github.com/alfrotan-glitch/TOEFL-House/actions/workflows/toefl-v2-production-quality.yml), and verify the run and pull request refer to the expected [draft PR #61](https://github.com/alfrotan-glitch/TOEFL-House/pull/61). On a pull-request run the tested build ref can be GitHub's synthetic merge commit, not the head commit. Verify that the tree and artifact are the intended release and that `main` has not changed; otherwise requalify a new candidate. Do not equate commit ID with artifact digest.
2. The artifact's `site/` folder contains `_worker.js` and, if packaging succeeded, all 25 paths from the historical public snapshot; `PACKAGE-INVENTORY.json` records byte length and SHA-256 for each. Independently verify all hashes after download and immediately before upload. Retain this immutable package, its inventory, CI run, source commit and any preview/provider evidence. The standalone `toefl-v2-release-worker` artifact is not a complete static-site package.
3. The 25 assets come from the public snapshot of an **older** deployment (`the-toefl-house`, 9 November 2026), captured on 17 November in GitHub Actions run 44041822731. The captured deployment-hash strings are historical identifiers: the packager does not independently validate their algorithm or prove they represent the active `toeflhouse` production project. SHA-256 establishes package-byte integrity, not origin or production parity. The package job also compares SHA-256 of each historical asset against a read-only GET of the canonical public URL, recording results in `PUBLIC-ASSET-COMPARISON.json`; it fails on a difference, failed request or redirect and retains the evidence when possible. A match proves only the returned public bytes at that time, not the Pages deployment manifest or runtime identity. **Do not deploy these assets until an authorized operator has compared every path and byte with the currently approved production manifest and confirmed all dependencies, rights and release assets.** Missing or differing files require investigation and a newly verified package; do not silently substitute them. The source snapshot has an expiry and the package job fails if any historical path/report is absent.
4. The artifact omits secrets, bindings, original CMS Functions, external legacy services and Cloudflare configuration. It is not a database backup or a proof of deployability by itself. No live binding, asset parity, preview or deployed Worker identity has yet been verified.

## Preview isolation and binding gates

- Coordinate with the existing operator before taking any deployment action; check that another release or rollback is not in progress. Capture the active production deployment identifier, configuration, assets and a verified rollback target before attempting a preview. Never alter a production database for testing.
- **Public CMS privacy gate — unresolved:** the candidate `/api/content` preserves unrecognized nested keys from published JSON records; its known-key denylist is not an allowlist or a guarantee against exposing non-public data. A synthetic `internal_note` field was returned by the candidate, demonstrating the limitation without inspecting real records. `secret_key` and `admin_secret` were added to the known denylist, but that does not fix arbitrary unknown keys. Before previewing with any non-synthetic content or releasing, obtain an owner-reviewed public schema and compatible projection/allowlist (including legacy consumer requirements), verify the classification and source controls for both published rows without exposing data in evidence, and test the actual isolated binding. Do not infer safety from passing denylist checks. The archive script also retains unrecognized nested fields and must not archive such data until this gate is satisfied.
- The documented canonical project is Cloudflare Pages `toeflhouse`, using Direct Upload. Preserve the required `CMS_DB` D1 binding, `LEGACY_CMS` service binding and Pages `ASSETS` behavior, as well as the verified current static assets. Preview bindings must point to an **isolated, non-production or demonstrably read-only** CMS database and legacy service with representative, authorized public content. Verify those properties and access restrictions at the infrastructure/service layer; blocking non-GET methods in the Worker does not prove a legacy GET endpoint has no side effects. No real messages or applications may be submitted.
- Create a uniquely identifiable preview (not the production branch/hostname) with the qualified package and recorded configuration. Apply appropriate access controls if data or administrative surfaces are sensitive; `noindex` is not access control. Verify noindex/robots behavior, unsafe method refusal, admin/auth isolation, asset integrity, real binding behavior, all 51 sitemap routes at 320/390/768/1024/1440/1920, the three languages/RTL, safe admissions and legacy tools, security headers, accessibility (automated and manual keyboard/screen-reader) and repeated realistic performance tests. Verify real image rights, translation and institutional facts separately.
- Record the source SHA, artifact SHA-256, every asset checksum, Pages project, preview URL and provider deployment ID, binding/environment identity, upload evidence and timestamp. An upload checksum alone is not proof of the deployed runtime bytes: obtain provider-supported evidence of deployed-byte identity or record that limitation and do not claim the gate passed. Do not expose secrets or database contents in evidence.

## Production and rollback

Only after owner approval, all gates and exact candidate identity are independently verified: coordinate the release window, recheck active production ID and absence of concurrent releases, promote/deploy the **same qualified bytes and verified assets** using the authorized Direct Upload procedure, preserving all bindings and configuration. Verify the deployed identity and canonical production routes, assets, languages, CMS and security without writes; compare against the approved preview and record results. Merge only under the repository's review and required-check policies. Vercel is not the documented canonical site, but its configuration and possible external consumers have not been fully audited; do not disable it or override a required policy based solely on this document.

If a confirmed regression is attributable to this release, first confirm production still points to the affected release, then coordinate restoration of the previously recorded known-good deployment and its configuration through authorized Cloudflare controls. Verify production after rollback. Do not overwrite a newer release, change data or assume a prior deployment remains valid without checking.
